# Artifact B: API and integration contracts (spec 29)

The contracts between the screens, the Django domain modules, the background workers and outside
services. Written for developers, reviewers and auditors.

| What | Where |
|---|---|
| Machine-readable contract (OpenAPI 3) | [docs/api/openapi.yaml](../../api/openapi.yaml), generated from the code; CI fails on any difference |
| Every endpoint in the spec 29.5 template | [endpoints/](endpoints/README.md), generated by `python manage.py api_contracts` |
| Requirements behind each endpoint | [requirement records](../../requirements/README.md), [traceability matrix](../../requirements/traceability.md) |
| Interactive docs | `/api/docs/` on a running server (Swagger UI, bundled, no outside sites) |
| In the app and the console | Access page → **API endpoints** tab; console → **API endpoints** (both need `access.roles.view`) |
| Why it is done this way | [ADR-032](../../decisions/ADR-032-requirement-ids-and-contract-docs.md) |

## API baseline (spec 29.1) and how HIMS meets it

| Rule | How |
|---|---|
| `/api/v1/` prefix | Every endpoint; health checks (`/health/live/`, `/health/ready/`) sit outside on purpose |
| Resource nouns, explicit action endpoints | `POST /facilities/`, `POST /leave-requests/{id}/approve/`, `POST /beds/{id}/status/` |
| Pagination, filtering, ordering, maximum page size | Pages of 25, `page_size` up to 100; the audit log counts to 10,000 and says "more than" (`count_capped`) |
| One error format (RFC 9457) | See [errors](#errors) |
| Request / correlation ID | `X-Request-ID` accepted or made, returned, in every log line, audit event, outbox event and job (HIMS-PLAT-004) |
| Authentication and object-level authorization everywhere | Default deny: each view declares its permission per action; facility-scoped rows outside the grant are 404. Only 13 endpoints work without sign-in (sign-in, invitations, password reset, browser reports, CSRF, effective features, and the scheduled-jobs timer address, which needs its own secret and is off unless set), each rate limited, and a test pins that list |
| Foreign keys checked against the hospital and scope | Each deployment has one hospital database (ADR-003); facility and department references are checked against the caller's scope |
| No provider secrets in the screens | Secrets live in server settings only; messages mask links in the log |
| No personal data or tokens in URLs, traces or client error reports | Tokens travel in request bodies; traces use route templates and filtered error text (HIMS-SEC-020) |
| OpenAPI generated and checked in CI | On an empty database, with `--fail-on-warn` |

## Errors

Every error is `application/problem+json`:

```json
{
  "type": "https://<problem base>/stale-resource",
  "title": "Stale resource",
  "status": 409,
  "detail": "This record was changed by someone else. Reload and try again.",
  "code": "STALE_RESOURCE",
  "request_id": "server-generated-correlation-id"
}
```

Validation errors add `errors`, one entry per field. Internal failures answer 500
`INTERNAL_ERROR` with the request ID only; the detail goes to the log and trace, filtered.

| Status | Codes every caller can meet |
|---|---|
| 400 | `VALIDATION_ERROR`, `MALFORMED_REQUEST`, `IDEMPOTENCY_KEY_REQUIRED`, `INVALID_IDEMPOTENCY_KEY` |
| 401 | `NOT_AUTHENTICATED`, `REAUTH_LOCKED` |
| 403 | `PERMISSION_DENIED` (also recorded as `access.denied`), `MFA_SETUP_REQUIRED`, `REAUTH_REQUIRED` |
| 404 | `NOT_FOUND` (also for rows outside the caller's scope, so they do not reveal themselves) |
| 409 | `STALE_RESOURCE`, `IDEMPOTENCY_KEY_REUSED`, `CONFLICT` and the domain codes each contract lists |
| 429 | `RATE_LIMITED` with `Retry-After` |
| 503 | `DEPLOYMENT_NOT_PROVISIONED`, `SCANNER_UNAVAILABLE` |

Each endpoint's contract lists the codes its own code can raise, found by reading that code.

## Idempotency and concurrency (spec 29.3)

* **`Idempotency-Key`** on 41 write endpoints (each contract says which, and whether it is
  required). Kept per person and operation for 48 hours with a fingerprint of the request: the same
  key and body replays the stored answer with `Idempotent-Replayed: true`; a different body is 409
  `IDEMPOTENCY_KEY_REUSED`; concurrent duplicates wait and replay; error answers are not stored.
* **`version`** on editable records: send the version you read; a different one is 409
  `STALE_RESOURCE` and nothing is saved. Rows are locked while they change.
* **Database rules** close the remaining races: unique codes, no double-booked shifts
  (exclusion constraint), numbers never issued twice.

## Synchronous and asynchronous (spec 29.4)

Every Phase 1 endpoint finishes within the request. Follow-up work runs after the commit from the
transactional outbox (for example the invitation after `staff.member.created`) or as a scheduled
job (audit sealing, message retries, clean-ups, retention purge). Messages are tried once inside
the request and logged; if the provider fails, the action still succeeds and the scheduled job
retries the message. Long
checks the person starts (backups, restore drills, index checks) run in the request on a developer
PC and are recorded as rows that survive restarts; turning them into background operations with
`202 Accepted` and a status URL is planned with HIMS-SEC-017 once the data grows.

## Domain events (spec 29.7)

Outbox events carry the spec 29.7 envelope: `id` (the event ID), `event_type`, `event_version`,
`occurred_at`, `customer_id` (the deployment), `facility_id`, `aggregate_type`, `aggregate_id`,
`correlation_id` (the request ID), `causation_id` and a minimal `payload` with no personal data
beyond IDs. Consumers record each event ID they processed and skip repeats (ADR-012). Events in
use: `staff.member.created`, `staff.member.employment_status_changed`, `staff.credential.added`
and `bed.status.changed`; each contract lists the ones its endpoint can publish.

## Webhooks (spec 29.8)

HIMS receives no provider webhooks yet. The only inbound posting without sign-in is the browser's
own security reports (`POST /security/browser-reports/`): size-limited, rate limited and stored for
review, never trusted as authorization. Provider webhooks (payers, labs) will follow the 29.8 rules
when those integrations are built.

## Outside services (spec 29.6)

| Service | Used for | Failure behaviour | Contract notes |
|---|---|---|---|
| Email (SMTP; console locally) | Invitations, resets, alerts | Tried at once (20 s timeout); a failure never undoes the action and is retried after 5, 15, 60 and 240 minutes, then shown as failed with Send again | Provider chosen at hosting (HIMS-OPS-011) |
| SMS | Same messages where a phone is known | Printed on the console until the PO chooses a gateway (HIMS-NOTIF-002) | India DLT registration needed |
| ClamAV | Virus check of every upload | Unreachable → upload refused (`SCANNER_UNAVAILABLE`), never stored unchecked; 30 s timeout | HIMS-SEC-013 |
| PostgreSQL tools | Backups and restore drills | Failure → `RECOVERY_FAILED`, recorded | HIMS-OPS-009 |
| Browser passkeys (WebAuthn) | Second factor | Checked on the server; no outside service | HIMS-IAM-014 |

Payer (Stedi, Indian TPAs), ABDM, FHIR, lab and imaging adapters get their own 29.6 documents in
this folder when they are built. Unknown provider statuses will never be read as success.

## Versioning and breaking changes

* The API is version 1 (`/api/v1/`). Within v1, changes are **additive only**: new endpoints, new
  optional request fields, new response fields. Clients must ignore response fields they do not
  know.
* **Breaking** changes (removing or renaming a field or endpoint, making an optional field
  required, changing a type or a meaning) need a new version prefix or a deprecation period agreed
  with every client. Today the only client is the HIMS app itself, released together with the
  server, so such a change is made in one pull request that updates both.
* CI regenerates `docs/api/openapi.yaml` and fails if it differs, so every contract change is
  visible in review. The reviewer checks the diff for breaking changes.

## Keeping this current

Run `python manage.py api_contracts` after changing an endpoint, a test that calls one, the
backlog or the PR history, and commit the result. CI runs the same check.
